# Phase 0 Beta 负载与旧数据处置决策

- 记录日期：2026-08-23
- 状态：Accepted for initial capacity planning

## 初始容量模型

首轮容量和故障注入测试使用以下模型；这些数值是 Beta 起始门槛，不是长期 SLO：

| 指标 | 起始目标 |
| --- | ---: |
| 活跃房间 | 100 |
| 每房参与者 | 10 |
| 同时在线参与者 | 1,000 |
| 峰值动作写入 | 20 次/秒 |
| 同一实例并发提交 | 2 个请求作为最小竞争场景 |
| 同步动作处理 | p95 ≤ 250ms，不包含 AI 调用时间 |
| 定时任务恢复 | worker 重启后继续 claim，不丢失已提交任务 |

动作负载应包含普通玩家输入、多人投票、重复幂等键、WebSocket 重复包、计时器到期和 AI command 入队。容量测试必须使用 PostgreSQL，而不是 SQLite。

## 旧数据处置

1. 创建默认 `legacy` 租户，历史用户和历史记录映射到该租户。
2. 历史对局保留为只读；不把旧 Python 进程内状态假装转换成新引擎快照。
3. 进行中的短生命周期房间继续由旧路径服务并自然排空。
4. 新引擎实例固定 `engine_version` 和 `game_version_id`，不跨引擎迁移同一个实例。
5. 回填工具必须支持 dry-run、分批、断点续传、摘要校验和重复执行；在 Phase 4 实施，不与本次纯引擎 spike 混合。

## 重新评估条件

当真实 Beta 数据连续观察一个发布周期后，按活跃房间、动作峰值、AI 调用比例和数据库连接利用率重新校准容量模型。未完成重新评估前，不承诺超过上述起始目标的容量。
